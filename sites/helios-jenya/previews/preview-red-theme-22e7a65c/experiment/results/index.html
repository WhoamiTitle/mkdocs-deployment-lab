    Результаты эксперимента¶

    Исторические измерения v1.0 и изменения v1.1

    Приведённые ниже числа относятся к исходной серии T4/P4. В v1.1 добавлены версии, несколько целей доставки, preview и rollback Pages. Описание изменений P5 и проверка поиска дополняют результаты; новые замеры времени доставки пока не проводились.

    Исходные наблюдения хранятся в evidence/measurements, а на эту страницу переносятся только вычисленные по ним сводные значения. Текущий срез содержит пять локальных повторов, предварительную push-серию GitHub Pages и три парных запуска GitHub Pages и Helios от одного commit SHA. Для парного сравнения используются только запуски 4–6 с одинаковой границей измерения.

    Локальная сборка¶

    Серия выполнена 1 октября 2026 года на darwin-arm64, Python 3.13.7, commit 3d28d598c8334f831973a0aca5f97d93b607823f. Зависимости были установлены заранее, каталог результата очищался перед каждой сборкой, системный файловый кэш не сбрасывался.

    Операция Запусков Минимум, с Медиана, с Максимум, с Успешно
    Strict build 5 0,707 0,721 0,728 5/5
    Локальный deploy + healthcheck 5 0,294 0,295 0,302 5/5

    Артефакт содержал 131 файл и занимал от 4 509 378 до 4 509 379 байт. Разница в один байт связана с изменяемыми метаданными релиза; набор исходных файлов и commit SHA во всех пяти запусках совпадал, dirty=false.

    Парная серия GitHub Actions¶

    Серия выполнена 1 октября 2026 года на commit c14c580549c97fdf649cae0fe23341d8560df794. Каждый ручной запуск одного workflow параллельно собирал GitHub Pages и Helios. Началом наблюдения служило серверное поле created_at, окончанием — первый успешный внешний healthcheck с совпадающими SHA, свежим release ID и контрольной строкой. Поле measurement_scope равно workflow-dispatch-to-healthcheck.

    Время сборки¶

    Цель сборки Запусков Минимум, с Медиана, с Максимум, с Размер артефакта, байт
    GitHub Pages 3 0,530 0,917 1,069 4 582 096

    Во всех сборках было 131 файл, dirty=false, strict build завершился успешно. Небольшое различие размеров ожидаемо: цели собирались с разными значениями SITE_URL. Исходные квитанции перенесены в ci-build-times.csv и t4-actions-runs.json.

    Время до доступности сайта¶

    Площадка Запусков Минимум, с Медиана, с Максимум, с Успешно
    GitHub Pages 3 41,405 41,409 45,744 3/3
    Helios 3 31,157 40,310 42,375 3/3

    Сырые наблюдения GitHub Pages: 41,405420; 41,408923; 45,743827 с. Для Helios: 40,310348; 31,157275; 42,375423 с. В каждом из трёх парных запусков Helios стал доступен раньше Pages на 1,095072; 10,251648 и 3,368404 с соответственно. Выборка мала, поэтому это описание конкретной серии, а не утверждение о безусловном превосходстве площадки. Погрешность момента обнаружения ограничена двухсекундным интервалом опроса.

    Предварительные строки Pages 1–3 с длительностями 66,806483; 78,507646 и 53,725831 с сохранены в CSV, но исключены из таблицы: они получены от разных commit SHA и с границей push-start-to-healthcheck.

    Передача и healthcheck Helios¶

    Операция Запусков Минимум, с Медиана, с Максимум, с Успешно
    rsync 3 5,251 5,319 5,360 3/3
    Встроенный HTTP healthcheck 3 1,053 1,098 1,347 3/3

    Каждый новый immutable-каталог получил 131 файл размером 4 582 308 байт. rsync --stats зафиксировал 1 554 334; 1 554 362 и 1 554 344 отправленных байта. Каждый встроенный healthcheck завершился HTTP 200 с первой попытки. Полные строки находятся в helios-transfers.csv.

    Автономность опубликованного сайта¶

    Для commit 0bd5d64 браузер с запретом внешних origin выполнил 16 запросов, все к whoamititle.github.io. Формула KaTeX, локальные шрифты, SVG-иконки и поиск по запросу «развёртывание» с четырьмя совпадениями работали. Переданный объём страницы вместе с поиском составил 229 851 байт. Подробности и границы метрики приведены в разделе «Работа без внешних CDN».

    Изолированный workflow 36941458695 выполнен на commit c14c580549c97fdf649cae0fe23341d8560df794 в путях .deployments/mkdocs-deployment-lab-sandbox и public_html/mkdocs-deployment-lab-sandbox. Два контрольных rsync заняли 4,961 и 4,608 с и передали по 4 582 834 байт артефакта. После проверки оба sandbox-пути отсутствовали, sandbox URL отвечал HTTP 404, а production-сайт и соседнее портфолио — HTTP 200.

    Настоящий preview сначала был удалён ручным workflow 36941924953. Последующий workflow 36942021021 по событию удаления ветки успешно удалил ноль уже отсутствующих релизов. Это подтвердило идемпотентность очистки. В логах sandbox-проверки и трёх запусков T4 найдено ноль маркеров закрытого ключа и ноль точных строк known_hosts.

    Сводное сравнение GitHub Pages и Helios¶

    Критерий GitHub Pages Helios
    Время до доступности 41,405–45,744 с; медиана 41,409 с 31,157–42,375 с; медиана 40,310 с
    Успешность парной серии 3/3 3/3
    Strict build 0,530–1,069 с; 4 582 096 байт 0,548–1,002 с; 4 582 308 байт
    Доставка официальный Pages artifact и OIDC deployment SSH/rsync в новый immutable-каталог, затем атомарная ссылка
    Post-deploy healthcheck внешний наблюдатель серии; отдельного шага в workflow нет обязательный шаг workflow: HTTP 200, контрольная строка и release ID
    Поведение при обрыве управляется платформой; намеренный обрыв в проекте не моделировался экспериментально подтверждено: незавершённый rsync не меняет активный релиз
    Откат повторный deployment прежнего artifact/run; в проекте не автоматизирован ручной workflow и автоматический rollback после ошибки healthcheck проверены
    Preview отдельная схема не реализована отдельный URL на ветку и автоматическая очистка после её удаления
    Удобство отладки единый интерфейс jobs и шагов, но нет shell-доступа к инфраструктуре Pages доступны Actions-логи и SSH-диагностика файлов и ссылок; больше ошибок конфигурации ключей, путей и FreeBSD
    Секреты и права GITHUB_TOKEN, pages: write, OIDC; запись в Git не требуется отдельный SSH-ключ пользовательской учётной записи и проверенный known_hosts
    Эксплуатационная ответственность инфраструктуру публикации обслуживает GitHub release-каталоги, очистку и доступность Helios обслуживает владелец проекта

    По удобству первичной эксплуатации выигрывает Pages: меньше серверных деталей и стандартные журналы. Helios лучше диагностируется на уровне файловой системы и даёт контролируемый атомарный rollback, но требует сопровождения SSH-доступа, FreeBSD-совместимости и release-каталогов.

    Локальная скорость не используется как оценка Helios: у неё другая граница измерения и отсутствуют сеть, очередь CI и удалённый сервер.

    Выводы¶

    1. В парной серии Pages доставлял версию за 41,405–45,744 с с медианой 41,409 с, Helios — за 31,157–42,375 с с медианой 40,310 с. Обе площадки завершили 3/3 публикаций успешно.
    2. Helios стал доступен раньше Pages во всех трёх парах; медианная разница составила 3,368 с. Три запуска недостаточны, чтобы переносить этот результат на другую нагрузку или состояние очереди GitHub Actions.
    3. Сама strict-сборка занимала не более 1,069 с, а rsync — 5,251–5,360 с. Основная часть времени от dispatch до доступности пришлась на остальные этапы workflow, однако без более детальной трассировки нельзя корректно разделить её между очередью, подготовкой runner, установкой зависимостей и публикацией Pages.
    4. Ручной и автоматический откат, прерывание передачи, повтор release ID, невалидный релиз и очистка preview сохранили production-сайт. Разрушительные сценарии выполнялись только в sandbox, соседнее портфолио не изменялось.
    5. Self-hosting KaTeX добавляет в артефакт 1 378 961 байт, зато опубликованная страница не делает внешних runtime-запросов и сохраняет формулы, шрифты, иконки и поиск при блокировке других origin.
    6. Для GitHub предпочтителен официальный Pages artifact: ему не требуется contents: write. Для Helios выбран SSH/rsync с отдельным ключом и атомарным переключением release-каталогов.
