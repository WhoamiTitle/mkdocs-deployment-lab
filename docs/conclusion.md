# Итоговый вывод

## Рекомендуемый стек

Для публикации учебных и воспроизводимых вычислительных экспериментов в
экосистеме Python рекомендуется следующая комбинация:

| Задача | Рекомендация | Обоснование |
|---|---|---|
| Авторство отчёта | Markdown + MkDocs Material | низкий порог входа, понятная навигация, локальный поиск и расширения Markdown |
| Среда сборки | Python 3.13 и виртуальное окружение | одинаковая версия локально и на runner |
| Зависимости | `requirements.txt` с точными версиями | воспроизводимая установка на чистом runner |
| Контроль качества | Ruff, codespell, mypy, pytest, `mkdocs --strict`, offline-check | ошибки кода, текста, типов, поведения, ссылок и внешних ресурсов обнаруживаются до публикации |
| Основная публичная площадка | официальный GitHub Pages artifact workflow | минимальные права на репозиторий, управляемый HTTPS и простая эксплуатация |
| Отечественная площадка | Helios по SSH/rsync | соответствует требованию размещения, поддерживает preview и управляемый файловый layout |
| Безопасная публикация Helios | immutable-релизы + атомарная ссылка + healthcheck + rollback | неполная загрузка не заменяет рабочую версию |
| Формулы и оформление | локальная копия KaTeX, системные шрифты и локальные SVG | сайт работает без внешних CDN |
| Прослеживаемость | commit SHA, release ID и UTC-время в `release.json` | опубликованный результат связан с исходным кодом |
| Лицензирование | MIT для кода, CC BY 4.0 для текста | права на программу и исследовательский материал разделены явно |

Оптимальна гибридная схема: GitHub Pages используется как простая основная
публичная площадка, а Helios — как отечественная публикация и стенд для
контролируемого атомарного deploy. Один commit собирается для обеих площадок,
поэтому их результат можно сопоставить по SHA.

## Почему не один способ публикации

GitHub Pages требует меньше операционного сопровождения и не выдаёт workflow
право `contents: write`. Однако платформа скрывает файловую реализацию и в этом
проекте не предоставляет автоматический rollback после пользовательского
healthcheck.

Helios позволяет проверить staging-каталог, атомарно переключить символическую
ссылку, сохранить `previous` и диагностировать состояние по SSH. Цена этого
контроля — управление ключом, `known_hosts`, Unix-правами, очисткой релизов и
различиями Linux/FreeBSD.

## Когда рекомендация меняется

| Условие | Более подходящий выбор |
|---|---|
| Нужны сложная библиография, автодокументация API и сквозные перекрёстные ссылки | Sphinx + MyST-Parser |
| Центральны исполняемые ноутбуки, PDF и несколько форматов вывода | Quarto или Jupyter Book |
| Вычисления требуют GPU, часов работы или закрытых данных | считать отдельно; CI публикует готовые версионированные артефакты |
| Большой объём медиа или высокая нагрузка | S3-совместимое объектное хранилище и CDN с ограниченной IAM-ролью |
| Требуется полностью отечественная цепочка | GitVerse или SourceCraft для Git/CI и Helios либо отечественное object storage для сайта |
| Нужны версии документации `v1.0`, `v1.1`, `latest` | MkDocs + mike либо Sphinx + sphinx-multiversion |
| Deploy-ключ не должен иметь shell-доступ ко всей учебной учётной записи | отдельный Unix-пользователь, серверный wrapper или S3 IAM вместо обычного SSH-ключа Helios |
| Нужны DOI, ORCID и долговременное научное архивирование | GitHub/GitVerse release + Zenodo или институциональный репозиторий; одного Helios недостаточно |

## Ограничения результата

- Временная серия содержит три парных запуска и описывает конкретное состояние
  GitHub Actions и Helios, а не универсальное преимущество одной площадки.
- Прерывание и rollback экспериментально проверены для Helios; управляемая
  внутренняя реализация GitHub Pages намеренно не нарушалась.
- Обычный deploy-ключ Helios ограничен SSH-опциями, но остаётся ключом
  пользовательской учётной записи. Полная изоляция требует серверной поддержки.
- Отказ внешних CDN проверен для текущего набора ресурсов; новые зависимости
  должны повторно проходить offline-check и браузерную проверку.
