# Пайплайн публикации

`CI` проверяет push и pull request. `Publish` выполняет собственный
`make check`, затем вызывает переиспользуемый `site-operation.yml`.
Pull request не запускает доставку и не требует deploy-секретов.

## События

| Событие | Pages | Helios |
|---|---|---|
| Push любой ветки, включая `main` | preview этой ветки | preview этой ветки на каждой цели |
| Push стабильного тега | версия из тега и обновление `latest` | тот же набор версий на каждой цели |
| Ручной Publish без `version` | preview выбранной ветки | preview выбранной ветки |
| Ручной Publish с `version` | публикация существующего тега | публикация существующего тега |
| Select latest version | выбор опубликованной версии | выбор той же версии на всех целях |
| Roll back GitHub Pages | предыдущий стабильный снимок, нынешние preview | без доставки |
| Roll back Helios | без доставки | предыдущий релиз одной цели |
| Удаление ветки / Clean site previews | удаление preview | удаление preview на выбранных целях |

Одна job `prepare` собирает артефакты для разных `SITE_URL`. Старые версии и
preview загружаются из `site-builds`; сборка новой ветки не теряет их.
Helios-параметры берутся только из Variable `DEPLOY_TARGETS`, а ключи и
`known_hosts` — из указанных в ней Secrets. Пример JSON не является конфигурацией.

Jobs доставки скачивают готовую публикацию и не выполняют MkDocs build.
Helios использует `fail-fast: false`, поэтому одна ошибка не отменяет другую
цель. Pages и Helios доставляются независимо, без общей транзакции.

## Защита и права

Сторонние Actions закреплены полными SHA. Зависимости Python устанавливаются
через `uv sync --locked`. Браузерная проверка устанавливает Playwright через
`npm ci` по отдельному lock-файлу; этот инструмент не нужен для доставки.
SSH-файлы создаются с режимами `0700` для каталога и `0600` для файлов.
Проверка ключа SSH-сервера остаётся обязательной.

`contents: write` требуется только jobs сохранения `site-builds`, подтверждения
успешной доставки и восстановления состояния. Pages deploy получает
`pages: write` и `id-token: write`.
Ветка `site-builds` исключена из push-сборок. Операции изменения снимков
используют общую concurrency group `site-publication`.
Отдельные production locks Helios совпадают с locks ручного rollback.

## Доставка и healthcheck

Helios загружает immutable-каталог, проверяет его, затем атомарно переключает
`current`. При обрыве передачи старый каталог остаётся доступен.
При провале production healthcheck вызывается rollback, после которого
проверяется marker восстановленного release ID.

Pages использует официальные upload-pages-artifact и deploy-pages. После
публикации проверяются HTTP 200, контрольная строка, release markers всех
версий и preview, `versions.json`, корневое перенаправление и алиас.
После неудачного healthcheck и при наличии предыдущей доставки она
публикуется повторно, а состояние Pages в `site-builds` восстанавливается.
Job остаётся неуспешной, даже если откат прошёл.

## Артефакты и метаданные

`publication-<run-id>-<attempt>` хранится 30 дней и содержит:

- `pages/`: полный Pages artifact с версиями и preview;
- `previous-pages/`: предыдущую полную доставку для автоматического отката;
- `targets/<target-id>/`: готовую стабильную или preview-сборку для SSH;
- `operation.json`: режим доставки.

Квитанции Helios сохраняют результат доставки и rollback, не содержат ключей.
Каждый сайт и каждая версия имеют `release.json` и HTML marker с SHA, ID,
временем сборки и признаком локальных изменений. Повторные операции получают
разные ID. Версионные страницы берутся из tagged commit, а корневая метка
обозначает операцию публикации.

Замеры времени прежней серии находятся в разделе результатов эксперимента.
Они описывают старый pipeline; текущая реализация ещё не измерялась на хостингах.
