# Эксперимент

Практический эксперимент проверяет время и устойчивость публикации статического
сайта при штатном развёртывании, ошибке healthcheck и прерывании загрузки.

## Исследовательский вопрос

Позволяет ли схема с неизменяемыми каталогами релизов и атомарным переключением
ссылки сохранить доступность предыдущей версии при сбое публикации?

## Гипотеза

Пока новый релиз загружается в staging-каталог, публичная ссылка продолжает
указывать на предыдущий релиз. Она переключается только после полной загрузки и
проверки обязательных файлов.

## Сравниваемые реализации

В количественное сравнение входят GitHub Pages с официальным Pages artifact
workflow и Helios с SSH/rsync. Локальная реализация того же атомарного layout
используется как контрольная базовая линия. Способы из T4, для которых нет
реального стенда, не получают числовых оценок.

## Основные метрики

| Метрика | Начало | Окончание | Назначение |
|---|---|---|---|
| Время сборки | запуск `publication_pipeline build` | создан проверенный `release.json` | отделить генерацию сайта от доставки |
| Время публикации | начало push либо `created_at` ручного workflow | HTTP 200, контрольная строка и ожидаемый commit SHA доступны по публичному URL | сравнить пользовательскую задержку GitHub Pages и Helios |
| Время `rsync` | запуск процесса `rsync` | процесс успешно завершён и статистика разобрана | отделить передачу от переключения и healthcheck |
| Время отката | запуск rollback | healthcheck предыдущего release ID | проверить эксплуатационную устойчивость |

Для удалённой площадки одно наблюдение определяется как

\[
t_{\text{publication}} = t_{\text{healthcheck}} - t_{\text{start}}.
\]

Здесь \(t_{\text{start}}\) — локальная отметка непосредственно перед `git push`
для push-серии либо серверное поле `created_at` из GitHub Actions API для
`workflow_dispatch`.

Диагностические метрики: размер артефакта в байтах, число файлов, фактически
переданный размер, отправленные и полученные `rsync`-байты, число попыток
healthcheck и число внешних runtime-ресурсов. Защитные условия: успешный strict
build, HTTP 200, совпадение SHA и свежего release ID, ноль отсутствующих
внутренних ссылок и ноль внешних runtime-ресурсов для автономного режима.

Локальная метрика начинается непосредственно перед deploy-командой, а удалённая
— перед `git push` или в момент регистрации ручного workflow на GitHub. Они
имеют разные значения поля `measurement_scope` и не сравниваются между собой
как равные. С GitHub Pages сопоставляется только Helios из того же workflow,
для того же commit SHA и с той же границей измерения.

## Условия измерения

- одна серия выполняется для неизменного commit SHA и набора зависимостей;
- сборка каждый раз использует `mkdocs build --strict --clean`;
- зависимости уже установлены, а системный файловый кэш принудительно не
  очищается; это явно записывается как условие, а не называется «холодной
  сборкой»;
- время внутри одного процесса измеряется монотонным `perf_counter_ns`, граница
  между push и отдельным наблюдателем — UTC timestamp;
- для каждой площадки требуется не менее трёх успешных production-запусков;
- сохраняется каждая строка исходного CSV, включая неуспешные наблюдения;
- из малой выборки выводятся минимум, медиана и максимум; p95 и статистическая
  значимость не заявляются.

## Воспроизведение локальной серии

```bash
RUNS=5 RUN_START=1 make benchmark-local
```

Команда для каждого повтора собирает сайт во временный каталог, запускает
локальный HTTP-сервер, выполняет атомарную публикацию и проверяет release marker.
Сырые строки добавляются в `build-times.csv` и `deployment-times.csv`.

## Наблюдение удалённой публикации

Перед push фиксируется локальное время, а для ручного dispatch берётся
`created_at` соответствующего запуска из GitHub Actions API. Наблюдатель опрашивает
`release.json` с cache-busting параметром и завершает замер только после
совпадения SHA, контрольной строки корневой страницы и `built_at`, который не
старше начала наблюдения:

```bash
started_at_utc="$(.venv/bin/python -m scripts.measure_publication timestamp)"
expected_commit="$(git rev-parse HEAD)"
git push origin main
.venv/bin/python -m scripts.measure_publication observe \
  --platform github-pages \
  --method pages-artifact \
  --run 1 \
  --url https://whoamititle.github.io/mkdocs-deployment-lab/ \
  --expected-commit "$expected_commit" \
  --started-at-utc "$started_at_utc" \
  --measurement-scope push-start-to-healthcheck
```

Для Helios используется та же команда с другой площадкой, методом и URL. В
парной серии с ручным запуском обеим командам передаются одинаковый
`created_at` и `--measurement-scope workflow-dispatch-to-healthcheck`.

## Проверка отказоустойчивости

1. Опубликовать отдельную preview-ветку.
2. Остановить rsync до атомарного переключения и проверить старый URL.
3. Вызвать контролируемую ошибку healthcheck.
4. Выполнить ручной и автоматический откат.
5. Проверить предыдущий release ID и публичный URL после каждой операции.
