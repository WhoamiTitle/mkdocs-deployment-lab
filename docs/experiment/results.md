## Сводное сравнение GitHub Pages и Helios

| Критерий | GitHub Pages | Helios |
|---|---|---|
| Время до доступности | 41,405–45,744 с; медиана 41,409 с | 31,157–42,375 с; медиана 40,310 с |
| Успешность парной серии | 3/3 | 3/3 |
| Strict build | 0,530–1,069 с; 4 582 096 байт | 0,548–1,002 с; 4 582 308 байт |
| Доставка | официальный Pages artifact и OIDC deployment | SSH/rsync в новый immutable-каталог, затем атомарная ссылка |
| Post-deploy healthcheck | внешний наблюдатель серии; отдельного шага в workflow нет | обязательный шаг workflow: HTTP 200, контрольная строка и release ID |
| Поведение при обрыве | управляется платформой; намеренный обрыв в проекте не моделировался | экспериментально подтверждено: незавершённый `rsync` не меняет активный релиз |
| Откат | повторный deployment прежнего artifact/run; в проекте не автоматизирован | ручной workflow и автоматический rollback после ошибки healthcheck проверены |
| Preview | отдельная схема не реализована | отдельный URL на ветку и автоматическая очистка после её удаления |
| Удобство отладки | единый интерфейс jobs и шагов, но нет shell-доступа к инфраструктуре Pages | доступны Actions-логи и SSH-диагностика файлов и ссылок; больше ошибок конфигурации ключей, путей и FreeBSD |
| Секреты и права | `GITHUB_TOKEN`, `pages: write`, OIDC; запись в Git не требуется | отдельный SSH-ключ пользовательской учётной записи и проверенный `known_hosts` |
| Эксплуатационная ответственность | инфраструктуру публикации обслуживает GitHub | release-каталоги, очистку и доступность Helios обслуживает владелец проекта |

По удобству первичной эксплуатации выигрывает Pages: меньше серверных деталей и
стандартные журналы. Helios лучше диагностируется на уровне файловой системы и
даёт контролируемый атомарный rollback, но требует сопровождения SSH-доступа,
FreeBSD-совместимости и release-каталогов.

Локальная скорость не используется как оценка Helios: у неё другая граница
измерения и отсутствуют сеть, очередь CI и удалённый сервер.

## Выводы

1. В парной серии Pages доставлял версию за 41,405–45,744 с с медианой
   41,409 с, Helios — за 31,157–42,375 с с медианой 40,310 с. Обе площадки
   завершили 3/3 публикаций успешно.
2. Helios стал доступен раньше Pages во всех трёх парах; медианная разница
   составила 3,368 с. Три запуска недостаточны, чтобы переносить этот результат
   на другую нагрузку или состояние очереди GitHub Actions.
3. Сама strict-сборка занимала не более 1,069 с, а `rsync` — 5,251–5,360 с.
   Основная часть времени от dispatch до доступности пришлась на остальные
   этапы workflow, однако без более детальной трассировки нельзя корректно
   разделить её между очередью, подготовкой runner, установкой зависимостей и
   публикацией Pages.
4. Ручной и автоматический откат, прерывание передачи, повтор release ID,
   невалидный релиз и очистка preview сохранили production-сайт. Разрушительные
   сценарии выполнялись только в sandbox, соседнее портфолио не изменялось.
5. Self-hosting KaTeX добавляет в артефакт 1 378 961 байт, зато опубликованная
   страница не делает внешних runtime-запросов и сохраняет формулы, шрифты,
   иконки и поиск при блокировке других origin.
6. Для GitHub предпочтителен официальный Pages artifact: ему не требуется
   `contents: write`. Для Helios выбран SSH/rsync с отдельным ключом и атомарным
   переключением release-каталогов.
